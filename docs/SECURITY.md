# Security boundaries and requirements

HECATE processes untrusted repository source, documentation, and issue text. Current analysis is static: the CLI does not run repository build scripts or tests. The agent repository tools are read-only. Neither a local clone nor a dedicated workspace is an OS-level sandbox.

The native runtime includes an OpenAI-compatible Chat Completions provider. Provider credentials are configured through `HECATE_API_KEY` and used as an Authorization bearer value. Exact matches are removed from session content, tool results, provider responses, and outgoing conversation content before runtime-managed history is retained or sent. This is accidental-exposure defense, not complete secret detection or a substitute for secret management; a caller can create a session containing a key before the runtime receives it, and unknown secret formats may evade repository-tool heuristics. Provider errors are deliberately generic. HTTPS is required for non-loopback endpoints, redirects are disabled, requests have bounded sizes, and synchronous HTTP requests have a configured timeout and bounded response body. Provider output remains untrusted and is subject to the same runtime tool validation and permission policy as any other model response.

For `contribute --generate`, the CLI validates the retained workspace before registering repository tools; the existing tool registration opens its read-only checkout root from the retained checkout path and revalidates workspace metadata at tool boundaries. This is not a replacement for retained-capability validation/application and does not protect against the documented same-user concurrent path-substitution threat.

When `contribute --generate` is used, contribution-plan context, tool definitions, tool-call arguments, and repository excerpts/results are sent to the configured model provider. Configure only a provider trusted with that repository data. The CLI does not provide a separate provider data-disclosure consent prompt; workspace creation approval is not consent to disclose data to an untrusted provider.

## Workspace approval and plan validation

`prepare` first retrieves/analyzes GitHub data (which may populate HECATE's source cache), then prints the repository, issue, planned workspace, branch, and plan metadata and requires an affirmative terminal response before creating the contribution workspace. It reserves a new issue-specific workspace, clones the public repository, creates `hecate/issue-<number>` at the analyzed commit, and stores a versioned plan and audit manifest in `.hecate/`. Existing workspaces are refused rather than overwritten; failures preserve the reserved directory for inspection.

An agent session must carry a plan reference marked `Approved`. Each repository-tool operation additionally validates the canonical checkout path, workspace manifest, repository and issue identity, plan artifact path/schema, and stored plan. This is an application-level approval boundary, not tamper-proof authorization against the local user or malicious processes on the host.

## Filesystem tools

Tools open a `cap-std` directory capability rooted at the validated canonical prepared checkout. Model-supplied paths must be relative and reject parent traversal, absolute/platform-qualified paths, `.git`, and `.hecate`. Windows handling also rejects trailing-dot/space aliases and reserved device names. Symlinks/reparse paths are not traversed for reads or listing; opened regular files are checked for hard links. On Windows, hard-link detection uses file-handle metadata and denies access if that check fails.

Scans exclude `.git`, `.hecate`, generated directories, and known sensitive path/name patterns. Direct reads have a 256 KiB limit. Search accepts files up to 1 MiB each and scans at most 24 MiB, 2,000 files, and 10,000 directory entries; result limits are bounded. Symbol and reference analysis is Rust-focused and bounded. `read_diff` uses fixed Git arguments, excludes known sensitive paths, rejects workspaces containing hard-linked files, and caps returned output at 256 KiB (64 KiB by default) with a 15-second limit and cancellation handling.

Recognizable credential assignments, token formats, and private-key blocks are redacted from returned text. Sensitive-file names and redaction patterns are heuristic. They cannot identify every secret embedded in ordinary text, unknown credential format, binary or encoded data. Do not claim a guarantee that secrets can never be exposed; minimize context and do not log raw repository contents.

## Git subprocesses

No model-controlled command or path is passed as an executable command. Workspace creation uses fixed Git operations, disables system/global Git configuration, isolates hooks, and skips Git LFS smudging. `read_diff` launches a fixed `git diff HEAD -- ...` invocation, clears the child environment except for required platform variables and `PATH`, disables system/global config, terminal prompts, pagers, external diff, text conversion, fsmonitor, and external attributes files, and bounds time/output.

Git is still a native process operating on workspace metadata. Fixed arguments and environment controls reduce exposure; they do not turn Git into a sandbox. Do not introduce arbitrary Git subcommands, external diff drivers, filters, hooks, or executable repository tooling without a separate security design.

## Write and execution boundaries

Milestone 4D.1 adds `PatchValidator`, a read-only validator for structured exact-replacement and new-file proposals. The bounded local-CLI threat model assumes no malicious concurrent process running as the same OS user with write access to the selected workspace parent. HECATE does not defend against that actor, and this is not an adversarial filesystem boundary or an OS sandbox.

Workspace preparation opens the selected parent, creates the issue directory relative to that capability, and opens directories without following symlinks/reparse points. It retains parent, workspace, metadata, and checkout handles and checks their directory entries before and after Git operations, before issuing `WorkspaceResult`, and during patch validation. These checks detect many substitutions and cause preparation/validation to fail when a mismatch is observed. Creation and handle acquisition are separate OS operations, however, and Git uses path-based subprocess arguments. The checks cannot prevent every concurrent path replacement, nor prove that a newly opened directory is the exact object created before opening. Do not describe preparation or Git operations as race-free or fully capability-confined.

After capabilities are established, patch validation performs reads relative to retained directory handles, rejects links/reparse points and hard links on opened handles, and rechecks workspace, metadata, and checkout entry identities before using them. This confines those validation reads to the retained objects; it does not retroactively secure preparation. Failed preparation returns no `WorkspaceResult`. Production preparation does not delete a workspace on failure, so it cannot clean up a replacement directory; reserved workspaces are left for user inspection.

Expected plan and manifest bytes come from in-memory structures, are written with exclusive capability-relative creation, compared byte-for-byte on read-back, and hashed from the expected bytes. Disk contents cannot become the expected baseline merely by being read back. Workspace identity uses Unix device/inode or Windows `FILE_ID_INFO` checks, failing closed when usable identity is unavailable. Windows ordinal path comparison is case-insensitive ordinal matching, not a guarantee of equivalence under every filesystem or volume's rules.

The validator opens each repository child relative to an already-held directory handle without following symlinks/reparse points and checks hard-link count on the opened file handle. It rejects unsafe/sensitive paths, checks hashes and resource limits, calculates results and a SHA-256 proposal identity in memory, and produces a preview. A validated patch alone is not authorization.

`PatchProposal` deserialization is an upstream boundary: callers must cap serialized input bytes before invoking serde. Validator limits apply after deserialization and therefore do not constrain allocations made by an unbounded JSON parser. The retained workspace handles are an in-process trust anchor; a persisted manifest and path alone cannot re-establish that identity after process restart. Any later application phase must repeat confinement checks and verify original hashes/existence immediately before applying. Windows duplicate detection compares normalized proposal paths with `CompareStringOrdinal` in case-insensitive ordinal mode. This catches ordinal-equivalent spellings such as tested ASCII and Unicode case variants; it is not a proof of equivalence under every filesystem or volume's case rules. Windows directory identity uses `FILE_ID_INFO`; preparation fails if the API fails or returns an all-zero volume/file identity. Filesystems that do not provide meaningful IDs are unsupported for identity validation.

Patch previews include file text needed to review the proposed result. Path exclusions are reused, but the validator does not guarantee detection of secrets embedded in otherwise ordinary text; treat previews and validated content as repository data.

## Controlled patch application (Milestone 4D.2.1 and 4D.2.2)

The `contribute` workflow requires real interactive stdin/stdout terminals for both workspace creation and patch approval. Patch approval requires the exact `approve <full-patch-sha256>` confirmation. Approval is process-local, non-serializable, non-cloneable, bound to the exact validated patch and retained workspace, and consumed once by the application API. A model response, tool call, session field, environment variable, or command-line flag cannot authorize application. The CLI creates a fresh workspace and keeps its live capabilities through validation, review, approval, and application; it does not re-open a saved workspace path to reconstruct trust. There is no automatic approval. A proposal may be user-supplied (`--proposal FILE`) or generated by the native runtime (`--generate`); generated output remains untrusted and follows the same validation and approval path.

User-supplied proposals are UTF-8 JSON using `PatchProposal` schema version 1. The CLI checks the file type, caps serialized input at 8 MiB before deserialization, and then relies on the validator's stricter file, edit, operation, content, and preview limits. Generated proposals are likewise size-bounded and strictly parsed before the same validator is called. A complete escaped preview is required before approval; an over-limit preview is rejected rather than presented as complete. This bounds proposal parsing but is not a general safe-file-picker boundary against every concurrent filesystem actor.

The application API supports only exact validated UTF-8 replacements and new-file creation. It revalidates the retained workspace and file snapshots, stages every result and existing-file backup in the destination directory using exclusive creation, syncs and hash-checks those artifacts, then performs the per-file operations. Existing files use atomic single-file replacement; new files use atomic no-replace creation. On Unix, capability-relative rename/hard-link operations and directory synchronization are used. Replacement copies the original Unix permission mode, but does not explicitly preserve ownership, ACLs, extended attributes, or timestamps. On Windows, file validation/staging use retained directory capabilities and identity checks, while the final `ReplaceFileW`/`MoveFileExW` operation uses an absolute path derived from the retained parent handle; metadata preservation relies on the operating system's replacement behavior and is not independently copied or verified. Windows directory metadata is not explicitly flushed by this implementation. These guarantees are bounded by the documented local-CLI threat model, which excludes a malicious concurrent same-user process with write access to the workspace parent; they do not make the workspace a sandbox.

All changed contents are staged before the first target change, but multiple file operations are not atomic as a group. If an operation fails, HECATE attempts reverse-order rollback only when the target still has the exact identity and content HECATE expects. Restorations and created-file removals are verified. Unexpected modifications are not overwritten. Backups that cannot be safely used or cleaned are reported as recovery artifacts. The report distinguishes complete application, no-target-change failure, verified rollback, and unresolved recovery. This is not a crash-safe transaction: process termination, OS failure, or power loss can leave partial changes or staging/backups requiring manual recovery. Do not modify the contributor's original checkout. No shell, repository code, build, or test command is run.

The `contribute` CLI reports verified application, failure before target modification, verified rollback, or recovery-required outcomes. It preserves recovery artifacts reported by the application layer and does not claim multi-file atomicity. Process termination, OS failure, or power loss can leave partial changes or staged recovery files. It never executes tests or other repository commands, and never commits, pushes, or creates pull requests. Review the workspace and any recovery artifacts before retrying.

Before any command or validation runner is added, design disposable OS-level isolation, resource and time limits, network policy, credential removal, process-tree cancellation, output bounds, and cleanup semantics. A Git clone/worktree is not sufficient isolation. Never add automatic push, pull-request creation, or destructive Git operations.
